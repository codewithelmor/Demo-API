# ADR-0015: Web front end: React SPA served by an ASP.NET Core BFF (YARP)

| Field | Value |
|---|---|
| Status | Accepted |
| Date | 2026-10-30 |
| Deciders | Product owner, architect (`react-architect`) |
| Consulted | prd-frontend.md, ADR-0008, ADR-0010, threat model T-31; reviews by `dotnet-security-reviewer` and `react-security-reviewer` at build time |

## Context
Phase 2 adds a web front end to the Orders API (prd-frontend.md). Customers use `/`; Admins use `/admin` (Release 2). The API is frozen; only configuration may change (FE-D5, G4).

Inputs from earlier decisions:
- The API issues 15-minute HS256 access JWTs and rotating refresh tokens in a JSON body (ADR-0008).
- Refresh is strict: using the same refresh token twice revokes the whole token family (S-D6).
- Rate limits are per IP. The API reads only `RemoteIpAddress` and has no forwarded-headers code (ADR-0010, T-31).
- Tokens must never reach the browser (NFR-F09, G3).
- Cookie and CSRF rules NFR-F10 and NFR-F11. Sessions follow the API lifetimes plus a 30-minute Admin idle timeout (FE-D4), with a warning 2 minutes before (UX-D4). Sign-in is required to browse (FE-D1). English only. Local Docker only. One developer.

## Decision drivers
- No token in the browser, and no API code change.
- Strict refresh must not cause random sign-outs (parallel tabs and requests).
- Same origin: no CORS, so `Cors:AllowedOrigins` stays empty.
- Small security surface and a small patch routine (one developer).
- The full stack still starts with one `docker compose up`.

## Options considered
### Option 1: Vite SPA + ASP.NET Core BFF (YARP), SPA served by the BFF (chosen)
- Good: tokens stay on the server; the browser holds only an HttpOnly cookie. Same origin, so no CORS. No Node server in production, so no RSC or Server Functions surface.
- Good: the BFF is .NET, so it uses the same stack, tests and pipeline as the API.
- Bad: the BFF is new security-critical code (sessions, refresh, CSRF). One more container. No SEO (not needed: everything is behind sign-in).

### Option 2: Next.js App Router, Next server as the BFF
- Good: one TypeScript app with server rendering.
- Bad: needs a Node runtime and a monthly RSC/Server Functions patch routine. Session and refresh logic in TypeScript next to a .NET API. No benefit for signed-in-only pages.

### Option 3: SPA alone, calling the API directly with tokens in memory
- Good: no BFF.
- Bad: tokens reach the browser (breaks G3, NFR-F09). The refresh token needs storage that survives a reload. Needs CORS. Every tab refreshes on its own and triggers strict reuse detection. Would need an API change (cookie transport, ADR-0008 "revisit when").

### Sub-decision A: where the SPA is served
| Option | Good | Bad |
|---|---|---|
| **BFF serves the built SPA from `wwwroot` (same origin)** (chosen) | One origin and one cookie; no CORS; CSP and headers in one place | The SPA ships with the BFF image |
| Separate static host (nginx), BFF on another origin or path | Independent deploys | Two origins: CORS plus credentialed fetch; SameSite edge cases; more config |

### Sub-decision B: BFF session store
| Option | Good | Bad |
|---|---|---|
| **Valkey (existing container) via `IDistributedCache`, entries encrypted with Data Protection** (chosen 2026-10-30) | Sessions survive BFF restarts; works with more than one BFF instance; models production | The BFF depends on Valkey (fails closed). Valkey has no persistence and uses `allkeys-lru`, so a Valkey restart or eviction ends sessions. Needs a new ACL user |
| In memory (`MemoryCacheTicketStore`) | Simplest; no new ACL | Every BFF restart signs everyone out; one instance only |

## Decision
We use **Option 1**: a Vite + React SPA built into the `wwwroot` of `DemoApi.Bff`, an ASP.NET Core 10 host with YARP, on one origin.

### Session and cookie
- ASP.NET Core cookie authentication with a custom `ITicketStore` (`ValkeyTicketStore`). The cookie holds only an opaque session key, protected by Data Protection.
- Store entry: access token and expiry, refresh token and expiry, the user summary from EP-08, `LastActivityAt`, `CreatedAt`. Serialized, encrypted with `IDataProtector` (purpose `DemoApi.Bff.Session.v1`), stored under `bff:session:{id}`. TTL = refresh token `ExpiresAt` (7-day sliding, capped by the 30-day family limit).
- Valkey: new ACL user `demoapi_bff` limited to `~bff:*`, `-@dangerous`; own secret file in `dev-secrets/bff/`, generated by `init-dev-secrets.sh`.
- Data Protection: `SetApplicationName("DemoApi.Bff")`, keys persisted to a **file volume** `bff-dp-keys` (not Valkey: no persistence and LRU eviction; not shared with the API's `dp-keys`). Production: Blob Storage + Key Vault, as in ADR-0008.
- Cookie `__Host-demoapi`: `HttpOnly`, `Secure` (`CookieSecurePolicy.Always`), `SameSite=Strict`, `Path=/`, no `Domain`. Persistent, expiry = refresh `ExpiresAt`, updated after each refresh. The flags are the same in every environment and never weakened for development.
- Local HTTPS: Chromium and Firefox accept `Secure`/`__Host-` cookies on `http://localhost`; Safari/WebKit does not. Compose serves HTTP on `127.0.0.1:8081` for Chromium and Firefox. An opt-in `https` compose profile serves `https://localhost:8443` with an exported ASP.NET Core dev certificate (one-time script) for Safari and Playwright WebKit (decided 2026-10-30; details in ADR-0017).
- Admin idle timeout: in `OnValidatePrincipal`, if the user has the `Admin` role and now − `LastActivityAt` > 30 min, the BFF calls EP-06, deletes the session, expires the cookie and returns 401 `session-ended`. Only user requests update `LastActivityAt` (at most one write per minute); the readiness banner check does not. `GET /bff/user` returns the idle seconds left, so the SPA can show the warning dialog 2 minutes before (UX-D4).

### BFF endpoints
All responses use `Cache-Control: no-store` and ProblemDetails with `traceId`.
- `POST /bff/login`: calls EP-04, then EP-08 with the new access token; stores both; sets the cookie; returns the user summary only. Passes 401, 403 `email-not-confirmed`, 400 and 429 through as ProblemDetails. Rotates the session ID on every sign-in (no session fixation).
- `GET /bff/user`: the summary from the session (email, roles, `customerId`, `emailConfirmed`, Admin idle seconds left), or 401 `not-signed-in` / `session-ended`. Re-read from EP-08 after every token refresh.
- `POST /bff/logout` → EP-06; `POST /bff/logout-all` → EP-07. Both delete the session and expire the cookie even when the API call fails.
- `GET /bff/health/ready` → EP-57 (NFR-F18); `GET /bff/health/live`.

### YARP route allow-list
Explicit routes plus methods from the endpoint catalog; everything else returns 404.
- The path stays the same (`/api/v1/...` → `http://api:8080/api/v1/...`), so `Location` stays valid. Spike: if the API writes absolute `Location` URLs, add a response transform that makes them relative.
- Anonymous, no token, BFF `auth-strict` limit: `POST /api/v1/auth/{register,confirm-email,resend-confirmation,forgot-password,reset-password}`.
- Never proxied (handled only by `/bff/*`): `/api/v1/auth/{login,refresh,logout,logout-all}`.
- Authenticated: EP-08, 12-19, 22-27, 29-33, 35-43, 45-48, 50-55. Unbuilt stretch endpoints (EP-20, 21, 28, 34, 44, 49) are not listed. Admin routes are proxied for any signed-in user; the API enforces roles.
- Session-ending transforms: a 2xx from EP-09 (change password) or EP-37 (delete account) deletes the session and expires the cookie, because the API has already revoked the tokens.
- Not forwarded: `/scalar`, `/openapi/*`, `/health/*`, any unknown `/api/*` path (404 ProblemDetails, never `index.html`).
- Request transforms: remove incoming `Cookie` and `Authorization`, then add `Authorization: Bearer {access}`. Do not add `X-Forwarded-*` (the API ignores them).
- Response transforms: remove any `Set-Cookie` from the API.
- Body limit 1 MB (same as the API). Request bodies are buffered so one replay is possible.

### Token refresh (single flight, FR-F003, G4)
- Before forwarding: if the access token has ≤ 60 s left (by `TimeProvider`), call `RefreshCoordinator.EnsureFreshAsync(sessionId)`.
- Coordinator: `ConcurrentDictionary<sessionId, Lazy<Task<RefreshResult>>>`. The first caller starts the refresh; every other request for the same session (other tabs included) awaits the same task. The entry is removed with `TryRemove(KeyValuePair)` so a newer entry is never removed.
- Inside the refresh:
  1. Re-read the session from the store. If it is already fresh, return.
  2. Call EP-05 with **`CancellationToken.None`** and a 10 s timeout. A browser abort must not leave the API rotated while the BFF keeps the old token.
  3. Save the new token set before releasing the waiters.
  4. Re-read EP-08.
- **No retry and no resilience handler on the BFF's auth `HttpClient`** (EP-04/05/06/07/08). A retried EP-05 counts as reuse and revokes the family. On a timeout or network error the session is kept and the BFF returns 503 `upstream-unavailable`. If the API had in fact rotated, the next refresh fails with 401 and the session ends (rare, accepted).
- On EP-05 401: end the session and return 401 `session-ended`.
- On an API 401 for a proxied call (for example, a changed security stamp): run one single-flight refresh; if it succeeds, **replay the request once**. Safe because the API returns 401 before any handler runs. Never replay on any other status.
- Assumption: one BFF instance. More instances need a Valkey lock (`SET NX PX`); see "Revisit when".
- The ADR-0008 "benign race" option is **not** adopted; single flight in the BFF makes it unnecessary.

### CSRF (NFR-F11)
- Every non-safe method (POST, PUT, PATCH, DELETE) on `/bff/*` and `/api/*`, including `/bff/login` (login CSRF), must carry `X-CSRF: 1` and an `Origin` equal to `Bff:PublicOrigin`. Otherwise: 403 ProblemDetails `/problems/csrf-check-failed` before forwarding. The SPA shows "Refresh the page and try again" for this slug, not "Not allowed".
- The BFF has no CORS policy, so a cross-site request with the custom header fails its preflight. `SameSite=Strict` is a second layer.

### Rate limiting in the BFF (FR-F008, FE-D2, G1)
- Built-in `Microsoft.AspNetCore.RateLimiting`, fixed window, partitioned by `RemoteIpAddress` (the BFF is the edge; `X-Forwarded-For` never trusted; IPv6 keyed by /64 as in ADR-0010).
- `auth-strict`: 10 / 60 s, one shared bucket for `/bff/login`, register, confirm, resend, forgot, reset, change password (EP-09), delete account (EP-37).
- `refresh`: 30 / 60 s, counted on each EP-05 call the coordinator makes for that IP; when exhausted, the triggering request gets 429.
- 429 is ProblemDetails `rate-limited` with `Retry-After`.
- API `RateLimiting__AuthStrict__PermitLimit` and `RateLimiting__Refresh__PermitLimit` raised to 1000 through compose configuration. `general` stays per user (the token carries `sub`). Identity lockout still protects each account. Threat model T-31 updated.

### Static SPA and headers
- `UseStaticFiles` for hashed assets (`Cache-Control: public, max-age=31536000, immutable`). `MapFallbackToFile("index.html")` only for GET outside `/api` and `/bff`; `index.html` served `no-cache`.
- Headers: CSP `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`; `X-Content-Type-Options: nosniff`; `Referrer-Policy: no-referrer`; `Permissions-Policy` (deny all); HSTS on HTTPS only.
- Spike: confirm Radix/shadcn components run without `'unsafe-inline'` styles.

### Trace propagation (NFR-F19)
OpenTelemetry in the BFF (ASP.NET Core and HttpClient instrumentation, YARP `ActivityPropagation`), `OTEL_SERVICE_NAME=demoapi-bff`, same Aspire dashboard. The trace starts in the BFF and `traceparent` is forwarded, so the API's ProblemDetails `traceId` equals the BFF trace. No browser tracing.

### Logging (NFR-F15)
Never log `Authorization`, `Cookie`, `Set-Cookie`, or bodies of `/bff/login` and `/api/v1/auth/*`. `Microsoft.AspNetCore.Hosting.Diagnostics` and `Yarp` at `Warning`, so query strings such as `/reset-password?token=` are not logged. OTel URL query redaction on.

## Consequences
- Good: zero tokens in the browser; no CORS; the API is unchanged; random sign-outs from strict refresh are designed out.
- Good: one .NET pipeline covers the BFF; production surface is static files plus Kestrel, no Node runtime.
- Bad: the BFF is security-critical and needs a fresh-context security review and focused tests: single flight (20 parallel requests → exactly one EP-05 call), FT-01 token scan, CSRF rejection, per-IP 429, Admin idle timeout, change password and delete account end the session.
- Bad: signed-in requests depend on Valkey (fail closed: 503). A Valkey restart signs everyone out.
- Bad: Safari on localhost needs the HTTPS profile. One more container and image.
- Bad: raised API auth limits also apply to direct calls to `127.0.0.1:8080` (Scalar, httpyac). Accepted for local development.

## Revisit when
- More than one BFF instance → distributed refresh lock.
- The API gains forwarded headers (API v1.1 epic) → restore the API auth limits and pass the client IP with `KnownProxies` = the BFF.
- Hosting beyond local Docker → Data Protection keys in Blob + Key Vault, a real certificate, HSTS.
- SEO or an anonymous catalog (G2) → re-evaluate server rendering.

## Amendment 1 (2026-10-30, threat model §10, S-D9..S-D13)
- `Bff:PublicOrigin` becomes the list `Bff:AllowedOrigins` (NFR-F29); `Sec-Fetch-Site` checked when present; missing Origin on non-safe methods → 403.
- Session entries are bound to their session ID; sign-in deletes any existing session and calls EP-06 (NFR-F30).
- Refresh results are saved only if the session still exists with the same version (conditional save, NFR-F31).
- YARP typed route constraints, encoded-segment rejection and wider header stripping (NFR-F32); `no-store` on proxied responses and `Clear-Site-Data` on logout (NFR-F33).
- Every response carries the full header set incl. `X-Frame-Options: DENY` and COOP (NFR-F36); no developer exception page; `/bff/login` builds its own ProblemDetails (NFR-F39).
- BFF anonymous limit 60/min per IP; an API 429 never triggers a refresh (NFR-F37).
- Admin absolute lifetime 12 h (S-D10); R2 step-up: EP-16 and EP-19 need a sign-in within 15 min, else 401 `reauth-required` (S-D11).
- Trusted Types report-only, then enforced (S-D13).

## Amendment 2 (2026-10-31, as built; BFF security review and SPA review)
- **Cookie and store:** the cookie value is the raw 256-bit session ID (not Data Protection-protected). The session entry in the distributed cache is encrypted with a Data Protection purpose that includes the session ID, and the payload's `SessionId` is re-checked. The store is a custom `SessionStore`, not `ITicketStore`.
- **Refresh and logout:** the single-flight entry removes itself when the flight ends; tokens issued by the API are revoked when a local save fails or loses a race with logout; logout does not spend the refresh rate-limit budget.
- **Proxy:** request headers are forwarded from an allow-list (`CopyRequestHeaders = false`), not a block-list.
- **Config:** `Valkey:AllowInMemory` (in-memory sessions only in Development unless set), `DataProtection:KeysPath` validated outside Development, `Bff:ReadyCacheSeconds`, `Bff:ReadyPermitLimit`, `Bff:AnonymousPermitLimit`, `Bff:AuthStrictPermitLimit`, `Bff:RefreshPermitLimit`. The container reads its Valkey connection string from `/run/secrets/bff` (key-per-file).
- **CSP nonce (security finding L-3):** `index.html` is a template with `<meta name="csp-nonce">`. The BFF serves it with a fresh 128-bit nonce per response and sends `style-src 'self' 'nonce-…'` on those responses only; every other response keeps `style-src 'self'`. The SPA copies the nonce to `__webpack_nonce__` for Radix's scroll-lock style. No `unsafe-inline`. Zod runs with `jitless` through `src/lib/zod.ts` so no `eval` probe is reported.
- **Not built yet:** OpenTelemetry and security-event logging with hashed session IDs (T-55, review L-5), Admin step-up `reauth-required` (S-D11, review L-7, must land before any Admin UI), the `https` compose profile, Trusted Types report-only header.
