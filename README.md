# Orders API

A .NET 10 REST API for managing products, customers and orders, with **Admin** and **Customer** roles. It is a proof of concept built with production-grade practices: Clean Architecture with vertical slices, CQRS, soft delete and an audit trail, rotated refresh tokens, rate limiting, caching and a full test pyramid.

There is no UI. The API is documented with OpenAPI and browsable with Scalar.

## Features

- **Auth:** register, email confirmation, login, rotated refresh tokens, change password, lockout after repeated failures. Our own JWT issuer on ASP.NET Core Identity (no `MapIdentityApi`).
- **Roles:** Admin manages users, products, customers and orders. Customers use `/customers/me/...` routes and see only their own data (another customer's data returns 404, not 403).
- **Products, customers, orders and reports:** stock is locked with `SELECT … FOR UPDATE` in product ID order when orders are placed, edited or cancelled. Sales and top-product reports use Dapper over views and functions.
- **Data safety:** rows are never deleted (soft delete through an interceptor and global query filters). The app database role has no `DELETE` privilege. Every write produces an audit row in the same transaction; personal data is never stored as values in the audit log.
- **Concurrency:** ETags from PostgreSQL `xmin`. `PUT` needs `If-Match` (428 if missing, 412 if stale).
- **Operations:** health endpoints, OpenTelemetry (optional Aspire dashboard), per-endpoint rate limits, request timeouts, ProblemDetails errors that carry a `traceId`.

## Quick start

**Prerequisites:** Docker Desktop (or Docker Engine with Compose v2). Nothing else is needed to run the API.

```bash
docker compose up -d
```

This runs `secrets-init`, then `postgres` and `valkey`, then the `migrator`, then the `api`, with no manual steps.

| What | Where |
|---|---|
| API | http://localhost:8080 |
| Scalar (API reference) | http://localhost:8080/scalar |
| OpenAPI document | http://localhost:8080/openapi/v1.json |
| Liveness / readiness | `/health/live`, `/health/ready` |

Sign in as the seeded Admin:

- Email: `admin@demoapi.local` (override with `SEED_ADMIN_EMAIL`)
- Password: generated on first start. Read it with:

```bash
docker compose exec api cat /run/secrets/dev/SeedAdmin__Password
```

Useful variations:

```bash
docker compose --profile observability up -d   # adds the Aspire dashboard on 127.0.0.1:18888
docker compose down -v                         # stop and wipe data; dev secrets are regenerated
```

## Running without Docker for the API

Use this to debug in your IDE. PostgreSQL and Valkey still run in Docker.

1. Stop any local PostgreSQL that holds port 5432.
2. Run once: `pwsh deploy/scripts/Initialize-DotnetRun.ps1`. It publishes Postgres (5432) and Valkey (6379) on `127.0.0.1`, runs the migrator and stores the connection strings, JWT key and Admin password in .NET user secrets.
3. Start the API:

```bash
dotnet run --project src/DemoApi.Api
```

The `http` launch profile listens on http://localhost:64062 and opens Scalar. The `https` profile adds https://localhost:64061.

Run the script again after `docker compose down -v`, because the dev secrets change.

## Configuration and secrets

- Configuration comes from `appsettings*.json`, environment variables and key-per-file secrets under `/run/secrets`. Nothing secret is committed.
- Dev secrets (database passwords, JWT signing key, Admin password, Valkey ACL) are generated by `deploy/compose/init-dev-secrets.sh` into a Docker volume.
- `compose.override.yaml` is git-ignored. Copy `compose.override.yaml.example` for local tweaks such as relaxed rate limits.
- Outside Development and Testing the API refuses to start with the fake email sender or without a Data Protection key path.
- Scalar and the OpenAPI document are mapped only in Development.

See [ADR-0012](docs/product/04-architecture/adr/0012-local-setup-and-secrets.md) for the reasoning.

## API overview

About 40 routes across these areas. The exact route, status codes, auth rule, rate limit and cache rule for each endpoint are in the [endpoint catalog](docs/product/04-architecture/endpoint-catalog.md); the committed OpenAPI document is [`api-tests/openapi/v1.json`](api-tests/openapi/v1.json).

| Area | Examples | Access |
|---|---|---|
| Auth | register, confirm email, login, refresh, logout, change password | Anonymous, then authenticated |
| Admin users | list, lock, unlock, change role | Admin |
| Products | list, get, create, update, delete, restore | Reads: any signed-in user. Writes: Admin |
| Customers | by ID, erase (anonymise), restore | Admin |
| Customers (self) | `/customers/me`, `/customers/me/orders` | Customer |
| Orders | place, edit, cancel, list | Admin, or the owning Customer |
| Reports | sales, top products, order history | Admin |
| Health | live, ready | Anonymous |

Errors use [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) ProblemDetails with a `traceId`. Who may call what: [permission matrix](docs/product/02-requirements/permission-matrix.md).

## Project structure

Clean Architecture decides the projects. Vertical slices decide the folders inside them: the first folder level is a business feature (`Products`, `Customers`, `Orders`, `Reports`, `Auth`, `AdminUsers`).

```
src/
  BuildingBlocks/
    DemoApi.SharedKernel/      BCL only: Result/Error, abstractions, paging
    DemoApi.BuildingBlocks/    reusable plumbing, no domain references
  DemoApi.Domain/              entities and rules
  DemoApi.Application/         command and query handlers, ports, response DTOs
  DemoApi.Infrastructure/      EF Core, Dapper, Identity, SQL objects, migrations
  DemoApi.Api/                 FastEndpoints, validators, composition root
tests/
  DemoApi.UnitTests/
  DemoApi.ArchitectureTests/
  DemoApi.IntegrationTests/
api-tests/                     .http suites, OpenAPI export, helper scripts
deploy/                        Dockerfile, compose helpers, pipeline steps, scripts
docs/product/                  plan, requirements, ADRs, threat model, test strategy
```

Request flow: endpoint (bind and validate) → command → `ExecuteAsync` → handler calls the domain and `SaveChangesAsync` → `Result` is mapped to HTTP in one place. Queries skip the bus and use EF `AsNoTracking` projections or Dapper through `ISqlRunner`.

Rules enforced by architecture tests and banned-API analyzers: no business logic in endpoints, Application never references Infrastructure, feature folders never reference each other, no `DateTime.UtcNow` (use `IDateTimeProvider`), no `ExecuteDelete`/`ExecuteUpdate`, no Newtonsoft.Json.

## Testing

```bash
dotnet test tests/DemoApi.UnitTests
dotnet test tests/DemoApi.ArchitectureTests
dotnet test tests/DemoApi.IntegrationTests      # needs Docker (Testcontainers)
dotnet test --filter "FullyQualifiedName~CreateProductTests"   # one class
dotnet test --filter "Category!=Quarantine"
```

The integration tests start PostgreSQL and Valkey containers and reset data with Respawn. Tests are tagged with `[Story]`, `[Endpoint]`, `[Security]` and `[Audit]` so each requirement maps to a test. There are no automatic retries; a flaky test is fixed or quarantined with a logged Bug.

Black-box checks with the `.http` files (httpyac) against a running stack:

```powershell
pwsh api-tests/scripts/Initialize-LocalHttpEnv.ps1                   # creates test users, writes git-ignored env files
pwsh api-tests/scripts/Invoke-HttpTests.ps1                           # all areas
& ./api-tests/scripts/Invoke-HttpTests.ps1 -Area products,orders      # selected areas
```

Details: [`api-tests/README.md`](api-tests/README.md). Test strategy and exit gates: [`docs/product/07-quality/test-strategy.md`](docs/product/07-quality/test-strategy.md).

## Security

- Authorization is explicit on every endpoint; object-level checks return 404 for other customers' data.
- Passwords use PBKDF2 (220,000 iterations); unknown-email logins do equal work to avoid timing and enumeration leaks.
- Refresh tokens are stored hashed, rotated on use and revocable.
- The database role `demoapi_app` has least privilege; an integration test compares the live grants to `expected-grants.txt`.
- The `api` container runs read-only with all capabilities dropped.
- Security events (failed login, lockout, role change) are logged by user ID only.

The threat model is in [`docs/product/05-security/threat-model.md`](docs/product/05-security/threat-model.md). The latest code and security review, with items left open on purpose, is in [`docs/product/07-quality/review-2026-10-27.md`](docs/product/07-quality/review-2026-10-27.md).

To report a vulnerability, contact the maintainer privately rather than opening a public issue.

## Contributing

- Kanban with a work-in-progress limit of one: one story per pull request. Commits and PRs reference the Azure DevOps work item as `AB#<id>` (IDs in [`azdo-map.md`](docs/product/azdo-map.md)).
- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/).
- `main` is protected: a pull request and a green build are required.
- Every endpoint meets the Definition of Done in PRD §15: DTOs, validator, explicit auth rule, authorization tests (including BOLA on `/me` routes), audit row on writes, OpenAPI description, `.http` entry, unit and integration tests.
- New `using` directives go in the project's `GlobalUsings.cs`.
- When code and the plan disagree, raise it instead of silently changing a decision.
